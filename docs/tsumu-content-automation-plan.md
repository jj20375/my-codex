# 紡日水晶：商品上架、社群與 SEO 自動化規格

研究日期：2026-11-03，Asia/Taipei。

本文件以使用者提供的商店、三個商品頁、兩篇 Facebook 公開貼文，以及三套系統現有程式為依據。這次完成內容研究、流程與驗收規格；以下新增功能尚未寫入業務程式，沒有更改商品或發布貼文。

## 1. 日常操作只保留一條主要流程

**選商品／匯入舊商品網址 → 拖入照片 → 只補缺少的規格 → 選內容用途 → 生成與預覽 → 套用或排程。**

coBuy CMS 是正式商品與素材入口；socai 延用內容生成、圖片、社群發布與排程；個人化 Codex Web 提供本機執行與任務監控。跨系統權限、ID 與結果回寫仍依[整合建議](./cobuy-ai-integration-proposal.md)實作，不另維護三份商品主檔。

介面提供「商品上架包」「社群一週草稿」「節慶活動」「購買指南」四個常用操作。新商品預設先做上架包，既有商品可以直接做社群內容。

一次上架包包含：

- 商品名稱、簡介、三個賣點、分段詳情、規格、適用品項的保養與 FAQ。
- SEO 標題、描述、搜尋意圖、圖片替代文字及站內相關內容建議。
- 分平台社群草稿：開頭、內文、CTA、Hashtag／主題標籤建議、圖片引用。
- 缺少資料、來源衝突、發布前要檢查的項目；每項都能點回來源。

每個商品的內容、社群草稿與排程都有可直接開啟的路由。個人工作台可延伸 `/commerce/products/:productId/content`、`/commerce/products/:productId/social`、`/commerce/calendar`；正式入口整合進 coBuy 現有商品編輯路由，避免要求店家來回操作兩套商品編輯器。上述新路由為建議，尚未建立。

## 3. 商品事實與內容模板

從舊網址或圖片匯入的內容先是「來源記錄」，經店家確認才成為正式商品事實。每項資料保留來源、讀取時間與確認狀態。

| 資料層 | 欄位與規則 |
| --- | --- |
| 商品事實 | 商品類型、正式名稱、系列、材質、尺寸／單位、售價、庫存、備貨期、照片、可選規格；來源不明保持空值 |
| 品牌設定 | 顯示名稱、有效商品／LINE 連結、署名、視覺方向、核定的售後政策；文案風格參考另存本機研究資料 |
| 活動設定 | 目的、適用品項、時間與時區、優惠條件、名額依據、CTA；不可從歷史文章直接啟用 |
| 內容草稿 | 商品版本、使用的事實、平台、主題、標題、內文、標籤、素材、修訂版本、待確認事項 |
| 排程與結果 | 草稿版本、平台帳號、預定時間、執行狀態、實際貼文 ID／網址、重試及失敗原因 |

最低必要欄位依操作而定：可以在規格不完整時產生待確認草稿，但要阻止把未知尺寸、供電方式、價格或優惠寫成確定事實。舊頁看到的售價只是研究快照，發布時以正式商品資料為準。

分類模板：

| 類型 | 應有內容 | 類型限制 |
| --- | --- | --- |
| 水晶手鍊 | 已確認晶石／配件、珠徑、手圍、調整方式、穿搭、保養 | 不自動加入玻璃罩或夜燈描述；「K金」等材質不可單憑照片判定 |
| 水晶永生花／生命樹 | 花材與晶石、整體尺寸、玻璃罩／底座、擺放與送禮、保養 | 夜燈、電源、配件與包裝逐項確認；不帶入手圍指南 |
| 晶柱／原礦 | 礦種、尺寸、重量、實物圖、天然紋理、是否一物一圖、底座與擺放 | 不因既有模板標題寫「夜燈」就認定有發光硬體 |

優先讓買家快速看到「這是什麼、尺寸與材質、適合放哪裡／送誰、如何下單」，再展開故事。FAQ 只回答已確認事項；售後承諾使用店家核定版本。

## 4. 對話如何直接改成果

使用者正在編輯哪個商品、哪個平台、哪個草稿，都應顯示在聊天上方。對話提出欄位修改建議並顯示差異，可逐項採用與還原。

| 使用者說法 | 系統行為 |
| --- | --- |
| 「這款當入厝禮，文案短一點」 | 改當前社群草稿的情境與長度，保留商品事實 |
| 「標題多一點貓咪元素，不要改商品名」 | 產生社群標題候選，正式名稱保持原版本 |
| 「把手圍說明拿掉」 | 更新當前商品詳情草稿並顯示移除區塊 |
| 「這款加上聖誕送禮角度」 | 建立節慶草稿；沒有優惠資料就使用一般售價與有效商品連結 |
| 「安排下週三篇」 | 建立三份不同主題草稿與待排程清單，讓使用者看見帳號、素材及時間 |

若正式售價、庫存或活動條件需要變更，要明確列出變更內容再走原有商品／活動操作。不能只憑模型回覆就改正式資料。草稿與實際發布是不同動作。

生成拆為「擷取與補缺」「商品內容」「SEO」「平台文案」「檢查」等可保存步驟。額度不足時顯示等待額度，保留已完成成果；恢復後接續未完成步驟，活動若已過期則回到待調整，不補發過期貼文。

## 5. 標題、Hashtag、時事與節慶

### 三種標題分開保存

1. 商品正式名稱保留品牌辨識與型號。
2. SEO 標題說清楚品類與差異，例如材質、用途及系列；不堆疊同義詞，也不填不存在的搜尋量。
3. 社群開頭切入單一情境，例如桌面佈置、貓咪設計、入厝送禮；不用虛構買家評價、倒數或限量。

Google 建議每頁標題具體、簡潔並避免關鍵字堆疊；搜尋結果仍可能自行選擇標題。[官方標題指引](https://developers.google.com/search/docs/appearance/title-link)

### 標籤是可編輯的建議

從「品牌 → 實際商品／材質 → 使用情境 → 有效節慶」挑選相關標籤，去重並避免與商品無關的熱詞。每份社群草稿都顯示標籤建議；實際發布依平台目前能力使用 Hashtag 或主題標籤，不假設所有平台共用相同數量與格式。

標籤候選不是搜尋量或觸及保證。Google 商品 SEO 也不能用 Hashtag 代替標題、商品內容與技術設定；Google 不使用 `meta keywords` 作排名用途。[Google SEO 入門](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)

### 節慶優先、時事有關聯才使用

- 建立台灣時區行事曆，活動資料包含確切日期、備貨與最後下單日。中秋、聖誕、春節等只是主題候選，實際日期與出貨截單日另行確認。
- 可採新品故事、材質／工藝、桌面／穿搭、選購疑問、送禮等內容輪替，避免每天重貼同一份商品詳情。
- 年末送禮可規劃「送誰 → 怎麼挑 → 商品細節 → 規格／FAQ → 有效出貨提醒」序列。優惠只在已設定活動時出現。
- 現有 Google Trends 台灣 RSS 是熱搜線索，不代表已查證新聞。使用時事前需保存來源網址、事件時間、查證時間與商品關聯；查無適合題材時採一般情境。
- 發布前重新檢查節慶時點、活動有效期、商品供貨與內容重複性。沒有實際數據，不宣稱「爆款」「熱銷第一」。

以下為新草稿示範；沒有加入尚未確認的規格、優惠或 LINE 連結，未發布。

**商品名稱候選**：紫晶粉貓｜水晶永生花生命樹

**SEO 標題候選**：紫晶粉貓生命樹｜紫水晶永生花擺飾・紡日水晶

**描述候選**：紫水晶簇、粉晶球與白貓造型，搭配粉白永生花，組成一座桌上的小花園。認識紫晶粉貓生命樹的材質、擺放情境與商品細節，為日常或送禮挑一份溫柔心意。

**商品首段候選**：

紫水晶簇托起粉白花冠，白貓捧著一顆粉晶球，像把小花園收進桌面。紫晶粉貓生命樹，適合想為工作空間添一點柔和色彩的你，也適合作為送給貓咪愛好者的心意。

**Facebook 草稿**：

送給總是忙著照顧別人的你，一座桌上的粉色小花園。

紫水晶簇、粉白永生花，還有捧著粉晶球的白貓——「紫晶粉貓｜生命樹」把這些小細節放在一起，陪你佈置每天都會看見的一角。

適合挑給喜歡貓咪的朋友，也可以留給自己。

查看商品照片與完整資訊：［系統帶入已確認的商品連結］

#紡日水晶 #水晶永生花 #生命樹擺飾 #辦公桌佈置 #貓咪禮物

**Instagram 圖文方向**：以實物主圖、白貓與粉晶細節、花材細節、確認後的尺寸圖組成輪播；內文縮短為設計細節與送禮情境，CTA 使用帳號已設定且實際可用的購買入口，不假設內文網址具備同樣操作方式。

**LINE 草稿方向**：商品名＋一段亮點＋實物圖＋直接商品按鈕；價格由正式資料帶入。只在活動有效時附優惠。

**圖片規則**：優先使用實拍商品圖；需要情境圖時，以已選商品照片為參考，維持晶石顏色、花材、數量與配件。生成後保存為獨立素材供檢查，不能用新生成的不同商品替代實物。尺寸、材質或活動字樣使用已確認資料排版。

## 7. 自有商城 SEO 要同時做內容與頁面能力

目前 coBuy 設定在 production 啟用 SSR，但商品頁資料由 SWR 載入。這不等於已驗證正式商品初始 HTML 含完整 SEO 資料；需在實作時檢查 production HTML。

建議補齊：

- 由路由伺服器載入商品公開資料，讓初始 HTML 包含商品名稱、內容與每頁 title、description、canonical。
- Product／Offer 結構化資料由已確認資料與即時售價、幣別、供貨狀態產生，和頁面顯示一致；不生成假的評分或評論。Google 建議商品資料出現在初始 HTML，結構化資料不保證得到特殊搜尋呈現。[官方商品結構化資料](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing)
- sitemap、可索引的正式商品網址、分類與文章內部連結、描述圖片內容的替代文字；草稿預覽不進搜尋索引。
- 商品介紹使用內容模板渲染語意清楚的標題、段落、清單，方便閱讀與維護；不要把整篇文字都當作標題。
- 建立獨立的購買指南／品牌文章內容，不塞入目前的短備註 `note` 欄位。候選主題為「水晶手鍊手圍怎麼量」「永生花與水晶擺飾的保養」「入厝禮物怎麼挑」。這些是內容方向，尚未驗證搜尋量或競爭程度。
- 用 Search Console 的搜尋字詞與點擊表現調整標題；用有來源的商品點擊、加購與付款事件評估成交。UTM 及訂單歸因接點目前仍需補齊，不能把按讚或生成篇數當成交率。

現在 iOPEN 階段先輸出可用的商品文字／HTML 與社群草稿，不假設能改平台的 head、canonical 或伺服器設定。自有商城上線後才由自身頁面輸出完整 SEO。

遷移時保留 iOPEN 商品 ID 與 coBuy 商品的網址對照，更新自己能控制的社群、LINE 與網站連結。iOPEN 網域的重新導向需由平台提供能力；不能承諾直接替該網域設定 301 或自動搬移搜尋權重。自己控制的舊網址才依對照處理永久重新導向。[Google 搬站指引](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)

## 8. 現有能力、實作優先順序與驗收

| 範圍 | 已有基礎 | 本次建議新增 |
| --- | --- | --- |
| 個人 Codex Web | 商品／活動登錄、聊天任務、用量與排程基礎 | 將當前商品與內容草稿綁入對話，保存分步成果 |
| socai | 商品文案／iOPEN HTML、平台文案、情境與熱搜線索、每日內容計畫 | 來源事實驗證、分類模板、活動期限、SEO 欄位、跨系統商品識別 |
| coBuy | 正式商品、媒體庫、既有 LINE／團購與訂單 | 長文內容與草稿版本、商品圖集關聯、AI 側欄、逐欄套用、商品 SEO 與文章頁 |

建議第一階段只做一個完整閉環：**一個商品的事實與照片 → 商品／SEO／FB 草稿 → 預覽與修訂 → 保存草稿**。接著打通 coBuy 套用，再接既有排程與發布。批次和全自動發布放在資料、預覽與重試可驗證之後。

驗收用這次三個商品與兩篇貼文：

1. 永生花草稿不含手圍指南；手鍊可帶入正確手圍區塊。
2. `11.5m` 顯示待確認，不被當作正式尺寸；夜燈與材質未知時不推測。
3. 新貼文不帶入已過期的 8/31 活動，不擅選互相衝突的 LINE 連結。
4. FB 發文預覽沒有意外的 Markdown 標記；標籤去重且與商品／情境相關。
5. 對話只修改指定草稿欄位，能看差異、還原；重整網址可回同一份草稿。
6. 中斷／額度等待後保留成果；恢復時重新驗證活動時效與商品版本。
7. 套用與發布分開；各平台有實際成功結果，重試不重複發文。
8. 正式商品 HTML 與結構化資料的售價、狀態及可見內容一致，並完成 Google 工具驗證。
